# 运维、保留与清理策略

本文件是 LIL-26 的交付方案，**不是对任意环境执行真实数据清理、部署或数据库修复的授权**。维护者于 2026-09-03 单独批准本次专用 QA 对象清理；此决定不适用于历史开发库、业务数据或后续环境。按已批准 S4 与当前代码记录行为；没有新增自动 TTL、清理 job、存储依赖或 Schema。

## 保留对象与实际行为

| 对象                                                                                           | 当前保留 / 可配置性                                                          | 不可误删与恢复限制                                                                   |
| ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `event_publication` 已完成投递                                                                 | `apocalypse.events.completed-retention-days=7`；`cleanup-cron=0 15 3 * * *`  | 只清理已完成记录；未完成记录保留供重投，不把它作为 Calendar 来源档案                 |
| `sys_login_log` / `sys_oper_log`                                                               | `apocalypse.audit.retention-days=180`；`cleanup-cron=0 30 3 * * *`           | 当前实现按时间物理删除；需要更长审计期时在到期前调整和归档，事后不能仅靠应用恢复     |
| Calendar baseline/release/correction、日历/成员、日程/修订、覆盖/冲突、projection source/grant | 当前无 Calendar TTL/物理清理任务；归档、取消、撤回或逻辑删除不代表空间已释放 | 保留引用、版本单调、owner/provenance 与幂等标识；清理投影 tombstone 可能导致重放复活 |
| `cal_data_import` 原 CSV/附件、元数据、hash、diff、review/publish 引用                         | 当前无过期自动清理；受 20/2/10 GiB 配额与每条预留约束                        | INVALID/REJECTED 也仍占存储；不能删来源来绕过配额，不把普通操作日志当原文件备份      |
| 本地 QA 日志/截图/DOM/源码指纹与决策                                                           | 当前保留到 LIL-27 确认交付、选定持久位置并校验副本；未设自动删除周期         | `*.log` 被 Git 忽略；本地存在不等于已版本化。没有已验证副本前不删本地唯一证据        |
| 专用 QA 容器/临时目录                                                                          | 仅供开发验收；保存证据与所需恢复副本，单独批准后停止/移除                    | `--rm` 可能同时删除专用匿名卷；证据不能仅放其中。不得匹配清理其他项目/开发库         |

7/180 天是仓库现有运行默认，不是对业务合规保留期的法律判断。对需要长期审计的下游系统，部署前由负责人确定实际周期。当前定时器未指定 zone，执行时区以进程调度配置为准；多实例可能各自触发，全局单执行锁不是当前承诺。

全局事件/审计清理与 Calendar 开关独立；关闭 Calendar 不会暂停它们。审计删除条件是 `< cutoff`，不可假定有软删除回收站。不要把待重投失败事件或来源记录纳入普通日志到期删除。

## 为什么当前不加 Calendar 自动清理

已存在“保留历史 + 配额”机制，可保证 provenance、审计、恢复和幂等；替代方案“按状态/年龄直接 TTL 删除”会破坏跨表引用和来源重放，且没有已批准的归档格式、保留期与恢复语义。因此文档收口保持现状，不临时发明自动清理任务。需要自动清理时另开有边界 discovery，比较引用感知归档、外置附件、限额和容量成本，再审 Schema/API/运行模型。

## 容量监测与人工处置清单

在获授权环境由运维人员执行只读容量检查，记录日期、目标库、逻辑计费量与物理空间；任何清理前单独批准精确对象集合。

1. 监测全局/上传者/目标配额、数据库/索引/TOAST、WAL、备份及剩余磁盘；文件逻辑计费不等于物理磁盘占用。日历规模同时监测查询 p95、投影批次 p95/失败率和锁等待。
2. 形成待处置候选清单，逐项核对是否被当前/历史 release、revision、冲突或投影来源引用；所有已发布来源默认排除。不提供盲目按日期 DELETE 的通用脚本。
3. 明确作用环境、ID 范围、保留依据、归档格式/权限、备份标识、恢复点、预计释放量和停机影响；取得数据负责人的独立批准。
4. 先在隔离恢复副本演练，验证来源/hash/引用与重放行为，再考虑真实执行。演练失败保持原数据，不能通过放松外键/删幂等键通过。
5. 执行后核对数量/hash、日期有效值与来源、历史修订、同版本重放/取消不复活、授权与恢复能力。保存执行者/审批/时间/结果；仅有备份文件而无恢复验证不算可恢复。

业务操作中的删除/撤回并不触发本清单中的物理清理；磁盘逼近配额时先阻止继续导入并评估容量，不擅自压缩/丢弃已发布证据。扩大配额也不等于磁盘自动扩容。

## 迁移与回滚

- Flyway 只向前；Calendar 使用 V8/V9/V10，禁用仍保留 Schema。不能修改已应用脚本、倒退 schema history 或删除 Calendar 表来关闭功能。
- 现有开发库的历史 V1 checksum 不一致须独立处理：先备份、取得实际 schema/history 与预期文件的差异，人工决定 repair/前向修复/重建可丢弃环境。本项目任务没有执行这些动作。
- 接入已有非 Flyway 数据库时，基线版本必须根据实际结构核验后显式选定，不能用 `baseline-on-migrate=true` 自动掩盖缺失迁移。
- 代码回滚与数据回滚分离：优先关闭 capability/排空受影响流量；只回退到能读取当前 Schema/数据版本的已验证制品。未知兼容性不承诺原地代码回退。
- 错误业务发布使用撤回/新修订/INHERIT，错误年度日别使用新审核发布；不改历史记录、不将数据库备份整体覆盖视为普通业务撤销。
- 数据恢复仅在隔离库先验证完整备份与引用，执行真实恢复需专门批准；同时核对授权版本和 Redis 会话，避免恢复后旧凭证意外重新生效。

## 常见故障

| 现象                   | 首先核对                                                         | 不可采用的捷径                                    |
| ---------------------- | ---------------------------------------------------------------- | ------------------------------------------------- |
| 开关开启但菜单不见     | 全部实例配置、最新 `/me`、角色菜单、业务范围角色、前端 component | 在前端伪造权限/新增第二开关                       |
| 页面未安装/版本不匹配  | 制品版本、构建期模块、代理路径、静态资源缓存                     | 拉取任意远程脚本                                  |
| 11015/日期来源异常     | 当前 baseline/provider/资源 hash、迁移；保存 traceId             | 偷偷切换在线第三方结果                            |
| CSV 11016/11017/11019  | UTF-8/模板/大小/日期，来源分级与目标范围                         | 改扩展名、伪造官方 attestation                    |
| 发布 40900/11006/11018 | 重新查询当前版本/hash/是否已生效                                 | 循环重发旧命令或手改数据库状态                    |
| 投影批次慢或规模上升   | 真实批量大小、调用者数、数据分布、SQL/锁等待；触发容量评估       | 宣称“500 条就是并发 500 人”或未经测量推算万条时间 |

## 本地 QA 对象交接

每轮将专用服务 PID/监听端口、完整容器 ID、挂载卷与临时目录登记在私有运行记录。清理时重新只读核对，不能照抄过期 PID，也不能用全局 Docker prune 或模糊目录匹配代替精确对象清单。

2026-09-03 本次清理只获准处置 Calendar 专用 QA 前后端、PostgreSQL/Redis 与临时文件；先保存源码/证据指纹、原始资料与必要的恢复副本。PostgreSQL 镜像可能自动创建匿名卷，`--rm` 容器停止时该卷也会被删除，不能误称其没有挂载。数据库备份可列出对象不等于已完成恢复演练。

实际清理结果与恢复位置由私有 Run 记录；不将含凭证的启动脚本、数据库 dump 或个人原始 QA 提交到公开仓库。历史开发库、其他项目及 workspace 根均不在清理目标中。
